# Assignment 3 — Event-Driven Architecture with RabbitMQ

## Architecture

```
[Client]
   │
   ▼ REST
[Order Service] ──gRPC──► [Payment Service] ──RabbitMQ──► [Notification Service]
   │                              │
   ▼ gRPC Stream             PostgreSQL
[Streaming Clients]
```

**Flow:**
1. Client calls `POST /orders` on Order Service.
2. Order Service calls Payment Service via gRPC to process payment.
3. Payment Service saves the payment to its DB, then **publishes** a `PaymentEvent` to the `payment.completed` queue.
4. Notification Service **consumes** the event and logs a simulated email.

## Idempotency Strategy

The Notification Service maintains an **in-memory map** (`map[string]bool`) keyed on `event_id` (a UUID generated by the Payment Service per publish).

When a message arrives:
1. The consumer checks if `event_id` is already in the map.
2. If yes → log "Duplicate skipped" and ACK (don't process again).
3. If no → process (print log), store the ID, then ACK.

This prevents the same notification from being printed twice if RabbitMQ redelivers a message (e.g., after a consumer restart before ACK was sent).

> **Note:** The in-memory store is reset on service restart. For production, replace it with a persistent store (Redis or a DB table) to survive restarts.

---

## ACK Logic

Manual acknowledgment is enabled (`auto-ack: false`).

```
Receive message
     │
     ├─ Parse fails → Nack (no requeue) — malformed, discard
     │
     ├─ Idempotency check fails → ACK (already processed)
     │
     └─ Process → print log → ACK
```

A message is **only ACK'd after the log is printed**. If the service crashes before ACKing, RabbitMQ will redeliver the message to the next available consumer — guaranteeing **at-least-once delivery**.

---

## Reliability

| Guarantee         | How it's implemented                                        |
|-------------------|-------------------------------------------------------------|
| Durable queue     | `durable: true` in `QueueDeclare` — survives broker restart |
| Persistent messages | `DeliveryMode: Persistent` in publisher                  |
| At-least-once     | Manual ACK — message redelivered if consumer crashes        |
| Idempotent consumer | In-memory `map[string]bool` keyed on `event_id`          |
| Graceful shutdown | `os/signal` in all three services                           |
